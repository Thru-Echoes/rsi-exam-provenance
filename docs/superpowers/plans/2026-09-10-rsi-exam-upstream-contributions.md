## What this directory is

`~/Developer/rsi-exam-fork` is a clone of the operator's fork `Thru-Echoes/RSI-Exam` (remote `origin`)
with the upstream `aiming-lab/RSI-Exam` as remote `upstream`. It exists for one purpose: to send the
organizers of RSI-Exam small pull requests that fix or extend their evaluation pipeline, as the
contribution offered to them by email on 2026-09-09 under their advisor track ("a pipeline or evaluation
change we adopt", 2 to 8 credits; credits must be confirmed by 2026-09-15 for RSI-Exam 1.0, otherwise the
2.0 window on 2026-12-15).

The provenance project (`~/Developer/rsi-exam-provenance`, the gate, the record, the verifier, the
instrument) stays in its own repository. Nothing of it is copied into this fork. Its whole claim is that
it sits beside the exam and leaves official runs untouched; a fork of the exam carrying it would read as
"we modified RSI-Exam".

TRACE is wired for this directory as project `rsi-exam-upstream` (see `.mcp.json`, `.claude/`); the
files `CLAUDE.md`, `HANDOFF.md`, `.claude/`, `.mcp.json` are excluded from git through
`.git/info/exclude` and must never appear in a commit or a pull request.

## The defect behind G1 and H1, reproduced

The program's loop step 3 says, verbatim:

> To revert, restore main/ from a snapshot (cp -r /app/methods/versions/v<K> /app/methods/main); that adds no new snapshot.

and the task instruction says "Save evaluated policy snapshots and results under `methods/versions/vN/`".
The grader stages `methods/main/` recursively and rejects any non-Python file
(`tests/policy_sandbox.py::_stage_policy`: "policy source may contain only Python files"), scoring the
submission 0.0. With `main/` existing, `cp -r versions/vK main` copies the snapshot *into* `main/` as
`main/vK/`, leaves `main/policy.py` untouched (the revert does not revert), and carries any result file
saved beside the snapshot into the graded tree. Transcript, run on macOS and identical under GNU cp:

```
$ mkdir -p methods/main methods/versions/v1
$ echo 'print(1)' > methods/main/policy.py
$ echo 'print(0)' > methods/versions/v1/policy.py
$ echo '{"score": 1}' > methods/versions/v1/results.json
$ cp -r methods/versions/v1 methods/main
$ find methods/main -type f | sort
methods/main/policy.py
methods/main/v1/policy.py
methods/main/v1/results.json
$ head -c 8 methods/main/policy.py
print(1)
```

In the provenance project's real rollouts this is why `gate/restore.py` exists and why result files live
under `methods/results/<id>/`. Say it this plainly in the pull requests: a submission can score zero for a
bookkeeping reason unrelated to the policy, and the program's own command produces it.

## Process rules

1. Sync first, every time: `git fetch upstream && git checkout main && git merge --ff-only upstream/main && git push origin main`.
2. One branch per change, cut from `upstream/main`, named `fix/<what>` or `feat/<what>`; one pull request
   per branch; never stack them.
3. Nothing is opened against `aiming-lab/RSI-Exam` or the Hub dataset without the operator's word. The
   session prepares the branch, the diff and the pull-request text, shows them, and stops. When the
   operator says open, open GitHub pull requests as drafts first (`gh pr create --draft --repo aiming-lab/RSI-Exam`),
   then mark ready. For a fork the head must be named: `gh pr create --draft --repo aiming-lab/RSI-Exam --head Thru-Echoes:<branch> --base main`.
4. Pull-request and commit text is self-contained: what changed and why, the failure it prevents, how it
   was verified; no session narrative, no assistant attribution footers, no internal labels. Mention the
   email of 2026-09-09 in one line so the organizers connect the two ("This is one of the changes offered
   in the contribution email of 9 September").
5. Their infrastructure is standard-library Python and shell; any script added stays that way, runs on
   Python 3.10 and later, and carries a docstring stating inputs, outputs and side effects.
6. Keep every diff minimal. A change to the program text or the instruction changes what future official
   runs see; the organizers decide how to version that, so the pull request must describe the change as a
   defect fix and offer the wording, not restructure the text.
7. Verify before proposing: for text changes, regenerate the template with `infra/prompts/build.sh` and
   diff; for task changes, run the task's own self-check and grader against a fixture (below); for scripts,
   a unittest under a `tests/` directory only if the repository already has one (it does not; put a
   `python3 -m doctest` or a short `if __name__ == "__main__"` self-test in the script and show its output).
8. Log with TRACE as you go: a proposed decision per change before editing, a contribution per branch,
   an annotation for anything surprising. Never fabricate a measurement.

## Hub pull-request mechanics

The organizers accept pull requests on the dataset. Two ways, both need the operator's HuggingFace login
(`hf auth login`, done by the operator; never paste a token into a file or a command line):

- The command line, one file per call, which opens a pull request on the Hub:

  ```
  hf upload RSI-Exam/RSI-Exam <local file> <path in the dataset> --repo-type dataset --create-pr \
    --commit-message "<self-contained one-line message>"
  ```

  Several files can go in one pull request by passing a local directory and a path prefix instead of a
  file. The command prints the pull-request URL.

- The Python API when a description is needed: `HfApi().create_commit(repo_id="RSI-Exam/RSI-Exam",
  repo_type="dataset", operations=[CommitOperationAdd(path_in_repo=..., path_or_fileobj=...)],
  commit_message=..., commit_description=..., create_pr=True)`.

Get the current task materials with
`hf download RSI-Exam/RSI-Exam --repo-type dataset --include "game2048_policy_search/*" --local-dir ~/Developer/rsi-exam-dataset`
and edit under `~/Developer/rsi-exam-dataset/game2048_policy_search/`. Keep a copy of the unmodified files
to diff against. `huggingface_hub` 1.10.1 and the `hf` command are installed on this machine.

## H2. A digest of the graded policy beside the reward (Hub)

**Files:** `game2048_policy_search/tests/policy_sandbox.py` (add one function), `tests/grade.py` (one
field).

**Change.** After staging, compute the digest of the staged source tree and write it into
`score_details.json` as `"policy_sha256"`. Construction, the same one the provenance verifier uses so the
two agree: for every regular file under the staged tree, in sorted POSIX relative-path order, the line
`<sha256 of the file's bytes><two spaces><relative path>\n`; the digest is SHA-256 of the concatenated
lines. That is exactly what `cd staged && find . -type f | sed 's|^\./||' | LC_ALL=C sort | xargs shasum -a 256`
prints (relative paths without a leading `./`, byte-order sorted), hashed as one string.
Leave `reward.json` alone: `grade.py::_reward_only` deliberately keeps only the numeric reward there and
the harness reads it; `score_details.json` is the detailed summary and is the right place. Standard library
only (`hashlib`, `pathlib`).

**Verification.** Grade a fixture `methods/` in the verifier image twice: the same bytes give the same
digest; one changed byte in `policy.py` changes it; the digest equals the value computed by the shasum
recipe above on the staged tree. Show the three outputs.

**Pull request.** Title: `game2048_policy_search: record a digest of the graded policy in score_details.json`.
Body: Summary, Why (a score should bind to exact bytes; released trajectories and third-party audits can
then check which policy was graded without trusting the directory listing; the construction is stated so
anyone can recompute it), Verification.

**STOP** if `score_details.json` is consumed by their site or leaderboard tooling in a way that rejects
unknown fields; ask in the pull request rather than guess.

## G2. A closing-step signal before the harness stops the agent (GitHub, issue first)

**Files:** `infra/prompts/budget.py`.

**What exists.** The reporter prints `[budget] N / M min elapsed (P%) — your run window is nearly over.
Wrap up soon and leave in /app/methods/main/ the version you want graded.` when elapsed time first passes
90, 95 and 99 percent of the window (`TIME_CHECKPOINTS`), and only when the agent's harness invokes it
between turns. Under a 12-hour window 90 percent is 72 minutes before the stop; under the reduced windows
used for pilots it is minutes.

**What the provenance rollouts showed.** Three rollouts lost record quality to the abrupt stop: one made an
unevaluated edit after its last decision and stopped without closing out, two had a candidate still
undecided when the window closed. The wording asks the agent to "wrap up"; it does not name a last action
or forbid new edits.

**Change to propose, as an issue first.** Two small things: (a) make the 95 percent line name the closing
action ("Stop starting experiments. Finish the one in progress, run the self-check once, leave the version
you want graded in /app/methods/main/, and do not edit main/ after that."); (b) read an optional
`ARB_BUDGET_CLOSEOUT_PCT` (default 95) so a short window can move the mark. Offer the diff in the issue;
open the pull request only if the organizers say yes, because any change to what the agent is told during
an official run is theirs to version.

**Verification.** `started_at()` takes the agent's start from the first timestamp in the harness transcript
(`$CLAUDE_CONFIG_DIR/projects/-app/*.jsonl` for Claude Code, the codex sessions directory otherwise) and falls
back to the mtime of `/logs/agent/*.txt`. Locally: point `CLAUDE_CONFIG_DIR` at a scratch directory holding
`projects/-app/t.jsonl` with one line `{"timestamp": "<ISO time a few minutes ago>"}`, set
`ARB_AGENT_TIMEOUT_SEC` so that the elapsed fraction sits between the marks, delete `/tmp/.arb_budget_time`
between runs, and run the script; show each mark's line firing once and the closing-action wording at 95.
The script exits 0 on any exception by design; keep that.

## Adversarial checks done before this handoff

- The nesting claim was reproduced on this machine (transcript above); GNU cp has the same semantics for
  an existing destination directory.
- The task materials are not in the GitHub repository (its tree has no `tasks/`; the README sends users to
  the Hub with `hf download`), so H1 to H3 cannot be GitHub pull requests. The Hub accepts pull requests on
  this dataset: its discussion list shows merged task-fix pull requests from outside contributors.
- `reward.json` is written by `grade.py::_reward_only`, which strips everything but the numeric reward on
  purpose; the digest goes to `score_details.json`. The verifier's `test.sh` also writes both files on
  failure with `{"reward": 0.0, "error": ...}`, so the digest must be optional in any reader.
- `autoresearch.j2` is generated from `autoresearch.md` by `build.sh` (the script's own comment says so);
  both must change together or the template ships the old text.
- `budget.py` fires only when invoked by the harness between turns, so a signal cannot interrupt a running
  tool call; the proposal names a closing action rather than promising a grace period, which would be a
  harbor change outside this repository.
- Changing the instruction or the program changes what future official runs see. Every such pull request
  is framed as a defect fix with the wording offered, and the versioning left to the organizers.
- The credits window: 2026-09-15 is five days away; G1 and H1 are the two most likely to be adopted in
  time and go first; G2 waits for an answer because it is the one that changes agent behaviour.
